# Phase 41 Replicated Durability and Single-Writer CAS Plan

## Objective

Phase 41 closes the Phase 40 gap between concurrent local persistence and a production-shaped logical snapshot update. The local implementation provides an authenticated, bounded, fail-closed **single-writer compare-and-swap** contract and a quorum-gated replica acknowledgement protocol. It intentionally does not claim that local code can prove stable media or cloud-volume replication.

## Typed contract

A `CasWriteRequest` binds a cluster, resource, logical snapshot, writer identity, writer epoch, request nonce, expected generation/hash, proposed generation/hash, payload hash, pinned public key, Ed25519 signature, and canonical request digest. The store accepts only the exact current expected generation/hash and the next generation. The proposed hash must equal the payload hash. Writer key rebinding, writer epoch rollback, same-epoch writer replacement, nonce reuse with a different request, and malformed bounded fields fail closed.

A `ReplicaDurabilityAcknowledgement` binds the exact request hash, generation, proposed content hash, replica identity, durability mode, flush sequence, observation tick, TTL, pinned key, Ed25519 signature, and event digest. The coordinator verifies every acknowledgement before mutation, rejects stale or future-dated evidence, rejects same-replica conflicting evidence, and requires the configured distinct-replica quorum. Only after quorum is present does the store atomically replace the CAS state and record the commit receipt.

## Persistence and recovery

`CasDurabilitySnapshotStore` validates cluster/resource/snapshot identity, state and receipt hashes, contiguous generations, bounded receipt cardinality, and receipt hash construction before save or restore. Save uses bounded JSON, staging cleanup, create-new staging, file `sync_all`, atomic rename, and directory `sync_all`. Load removes stale staging, bounds the file, decodes the snapshot, and validates the complete hash-bound state before returning it.

## Acceptance criteria

| Criterion | Required evidence |
|---|---|
| Writer authentication | Pinned Ed25519 writer key and canonical request signature verification |
| Single-writer CAS | Exact expected generation/hash, next-generation-only proposal, no mutation on mismatch |
| Replicated durability | Distinct signed acknowledgements meeting configured quorum |
| Storage evidence binding | Request hash, proposed hash, replica identity, flush sequence, and TTL bound in each acknowledgement |
| Conflict handling | Same-replica conflicting acknowledgements, nonce conflicts, key rebinding, stale/future evidence rejected |
| Retry semantics | Exact request retry returns the original receipt idempotently |
| Recovery | Atomic snapshot save/load, contiguous-generation checks, receipt/state hash validation, tamper rejection |
| Sanitization | No keys, signatures, payloads, full tokens, or cluster mutation in benchmark/compliance output |

## Production boundary

The local `sync_all` call is an observation of the local kernel/filesystem contract. It is not proof of stable media, controller flush barriers, managed-volume replication, replicated-filesystem commit, cross-region quorum, database transaction durability, or independent failure-domain placement. Production adapters must obtain signed acknowledgements from independently supervised durability replicas whose flush sequence is generated by a trusted storage adapter, not by the candidate writer itself. Process fencing, routing convergence, replica placement, key custody, and cross-process CAS ownership remain deployment gates.
