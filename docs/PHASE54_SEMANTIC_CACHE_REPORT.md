# Phase 54 semantic-cache implementation and performance report

## Executive summary

Phase 54 adds a bounded, thread-safe semantic-validation cache between the Phase 53 typed UEG validator and incremental target generation. The cache is content-addressed by a SHA-256 digest over the typed AST and target capability profile, returns cloned immutable reports on hits, and uses bounded LRU-style eviction. The generator now validates once per emission call and can use a prepared cache key on the hot path; semantic errors still fail closed before any target emitter, sink callback, or pooled output delivery.

The release benchmark uses deterministic 1/2/4/8/16/32-function fixtures, 128 samples per target and fixture, and four target profiles. Prepared-key cache hits measured **74–77 ns p50** across the suite, while uncached validation grew from roughly **311–322 ns p50** at one function to **8.5–8.8 µs p50** at 32 functions. The p50 comparison is recorded as an integer x1000 speedup, ranging from approximately **4.2× at one function** to **115× at 32 functions**. Key derivation is intentionally measured separately: it grows from about **10.3 µs** at one function to **308–313 µs** at 32 functions, so the next optimization target is fingerprint construction, not cache lookup.

## Architecture delivered

`SemanticValidationCache` has a positive fixed capacity, an `Arc<Mutex<CacheState>>`, a `VecDeque` bounded to capacity, content-addressed `SemanticCacheKey`, clone-on-read `SemanticValidationReport`, and sanitized hit/miss/insertion/eviction metrics. On a hit, the entry is moved to the back of the deque and cloned. On a miss, the exact Phase 53 validator runs and the report is inserted. When full, the oldest entry is evicted. A poisoned mutex is recovered through its inner state rather than bypassing validation.

The key incorporates a version domain separator, target label, all capability booleans, ordered unary/binary operator sets, node count, and serialized typed `AstFragment` values including function names, parameters, statements, expression sources, expression kinds, and source spans. Therefore a changed typed UEG or capability profile cannot reuse a previous report in the tested contract. The digest is an optimization key only and is not an authority token or signature.

`IncrementalCodeGenerator::with_semantic_cache` enables the cache. `next_chunk` still validates before rendering. `emit_remaining` validates once and then calls an internal unchecked cursor step, avoiding repeated validation for every emitted node. The default constructor remains uncached and preserves the Phase 53 behavior.

## Benchmark methodology

The benchmark runs the release example over already parsed deterministic UEG fixtures. It separately measures direct uncached semantic validation, prepared-key cache hits, and key derivation. Each row contains 128 samples. `valid_samples` includes the one initial cache miss plus the 128 measured hits, yielding 129 valid reports per row. Each row uses capacity 8, one cache entry, 128 hits, one miss, and zero evictions.

At 32 functions, the prepared-key hit path is approximately 113–119 times faster at p50 than direct validation in this local benchmark, while computing the key itself costs roughly 308–313 µs p50. This distinction is critical: the cache is valuable when the same typed UEG/profile is validated repeatedly, but a first-time or changed-input path remains dominated by fingerprint construction and semantic validation. These are local optimization measurements, not compiler throughput or production scalability claims.

The visual companion is `benchmarks/phase54_semantic_cache.png`, generated by `scripts/analyze_phase54_semantic_cache.py`. It shows the flat prepared-key hit line, the linearly growing uncached validation line, and the much larger fingerprint derivation cost.

## Verification matrix

| Boundary | Result |
|---|---|
| Zero capacity | Passed: `SemanticCacheConfigError::ZeroCapacity` |
| Key separation | Passed: target labels and capability changes produce distinct keys |
| LRU bounds | Passed: capacity 1 evicts the oldest entry and never exceeds one entry |
| Concurrency | Passed: eight concurrent validators return equivalent reports with one miss, seven hits, and one entry |
| Profile-specific diagnostics | Passed: disabling calls recomputes and returns `UEG-TARGET-UNSUPPORTED-CALL` |
| Fail-closed codegen | Passed: cached undefined-name reports return `GenerationError::SemanticValidation` before emission |
| Hot-path emission | Passed: `emit_remaining` validates once before its internal cursor loop |
| Historical regressions | Phase 50–53 focused suites passed during implementation; full all-target validation is required before publication |
| Safety boundary | No filesystem, process, network, secret, or cluster mutation is introduced |

## Phase 54 goals and next architectural boundary

Phase 54’s goals are bounded repeated-validation cost, deterministic cache invalidation, explicit profile separation, and measurable warm/cold behavior. It intentionally does not add persistent or distributed cache coherence, remote cache trust, generated-code caching, full type inference, runtime execution, or authority grants.

The next measurable goal is to reduce key-derivation overhead through an incremental fingerprint or per-function digest composition while preserving exact invalidation on changed source spans, expression structure, function order, and target profile. Any such optimization must compare cold, warm, changed-input, and capacity-eviction paths and must not allow stale reports to bypass semantic validation. Compliance metadata remains at 209 gates because this phase changes local performance behavior only.
